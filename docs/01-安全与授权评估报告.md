# 三盈会 APP（sfb）安全与授权评估报告

> 评估对象：`F:/workspace/sfb/app`（Flutter 3.44+ / Dart 3.12+，版本 3.2.0+102）
> 评估时间：2026-10-30
> 评估方式：212 个 Dart 文件全量审计 + 原生配置检查 + 依赖与资源核查
> 姊妹报告：`server/docs/01-安全与授权评估报告.md`（服务端）、`admin/docs/01-安全与授权评估报告.md`（管理后台）

## 一、结论摘要

**没有恶意后门**——没有动态加载、没有隐藏的远程控制指令、没有偷偷上传通讯录/短信/相册的代码、`package/` 下的本地依赖也没有网络行为。

**但三端里这一端的"作者控制面"最大**，三条关键链路全部指在作者的服务器和账号上：

| 链路 | 现状 | 后果 |
| --- | --- | --- |
| **数据** | `lib/base.dart:16` 生产环境 API 硬编码为 `https://demo.admin.syh.hzhero.cn` | 你的用户登录、订单、提现、身份证全进作者服务器 |
| **推送** | 极光 AppKey `f4b96adeec4eb2a41d831551` 是作者的（两处） | 作者可向你所有用户推送任意消息 |
| **更新** | `Global.update()` 从后端拉 `androidUrl` 后直接打开浏览器 | 配合上面，**作者可给你的用户推任意 APK** |

这三条单独看都是"模板默认值没改"，但叠在一起，效果和一个后门没有区别：数据在作者手里、推送权在作者手里、更新通道也在作者手里。

除此之外还有几处硬缺陷：

| 等级 | 问题 | 位置 |
| --- | --- | --- |
| **P0** | `flutter_z_location` 的 git 仓库已 404，**项目当前无法 `pub get`** | `pubspec.yaml:13-15` |
| **P1** | `assets/key/public.pem` 是**损坏的**（少 25 字符，DER 仅 143 字节），人脸核验接口会抛异常 | `assets/key/public.pem` |
| **P1** | 签名口令 `123456` 明文写在 build.gradle，`applicationId` 是 `com.junchen.sanyinghui` | `android/app/build.gradle:37,52-66` |
| **P1** | Android `usesCleartextTraffic="true"` + iOS `NSAllowsArbitraryLoads=true` | 两端配置 |
| **P2** | 品牌、URL Scheme、图片资源全指向作者 | 多处 |
| **P2** | 上传接口路径 `/api/alioss/upload` 会拼成 `/api/api/...` | `lib/httpUrl.dart:168` |

### 2.3 关于 `android/app/libs/` 里的 15 个 aar/jar

里面有 `AlibcTradeBiz`、`securityguardaar3`、`nocaptchaaar3`、`ut-analytics`、`utdid4all` 等——这是**淘宝联盟百川电商 SDK 的整套依赖**，不是可疑文件。

但两点要注意：

1. `android/app/build.gradle` 里**没有** `fileTree(dir: 'libs')` 或 `flatDir` 配置，这些 aar 实际不被 app 模块直接引用（应由 `flutter_alibc` 插件内部引入）。属于仓库里的冗余副本。
2. `ut-analytics` + `utdid4all` 是阿里埋点与设备标识 SDK，会采集设备信息。**必须在隐私政策里披露**，否则应用商店审核会卡（工信部对 SDK 采集有明确要求）。

## 三、问题详述

### 3.1 P0：生产 API 指向作者的演示服务器

**位置**：`lib/base.dart:16`

```dart
static final baseHost = kDebugMode
    ? 'http://192.168.1.15:8008'
    : 'https://demo.admin.syh.hzhero.cn';   // ← 发布模式用这个
```

`BBase.suUrl = '${BBase.baseHost}/api'`，而 `httpUrl.dart` 里 200+ 个接口全部基于 `suUrl`。

**后果**：打 release 包时，APP 会把登录、下单、提现、实名认证（含身份证号、人脸核验）、银行卡绑定全部发到作者的 `demo.admin.syh.hzhero.cn`。

而且这是**演示域名**——作者随时可能停掉它，停掉你的 APP 就白屏。

**修复**：

```dart
static final baseHost = kDebugMode
    ? 'http://192.168.1.15:8008'
    : 'https://api.你的域名.com';
```

建议进一步改成从 `--dart-define` 注入，避免再犯：

```dart
static const baseHost = String.fromEnvironment('API_HOST', defaultValue: 'https://api.example.com');
```

### 3.2 P0：极光推送 AppKey 是作者的（两处）

**位置**：
- `lib/util/global.dart:94` — `static const jpushAppKey = 'f4b96adeec4eb2a41d831551';`
- `android/app/build.gradle:46` — `JPUSH_APPKEY : "f4b96adeec4eb2a41d831551"`

**后果**：所有设备注册到**作者的极光应用**下。持有该 AppKey + Master Secret 的人可以向这批设备推送任意通知——包括钓鱼链接、伪造的"账户异常"提示。这是比"数据泄露"更直接的攻击面。

**修复**：极光后台建自己的应用，两处同步替换；`JPUSH_PKGNAME` 会跟着 `applicationId` 变，记得一起改。

### 3.3 P0：更新通道可被用于下发任意安装包

**位置**：`lib/util/global.dart:713-762`（`Global.update`）

```dart
Map res = await BService.updateConfig();        // 从 baseHost 拉配置
url = res['androidUrl'];
...
LaunchApp.launchInBrowser(url);                 // 直接浏览器打开下载
```

逻辑本身是标准的热更新提示。但结合 3.1（baseHost 指向作者域名）和 3.2（推送权在作者），就构成完整链路：

> 作者改一下自己服务器上的 `androidUrl` → 你的用户收到"新版本上线"弹窗 → 点"去更新" → 下载安装任意 APK。

**修复**：改完 3.1 后，这条链路就回到你自己手上。另建议：
- `androidUrl` 强制校验域名白名单
- 优先跳应用商店而不是直链
- 服务端对 `update/config` 的写权限收紧

### 3.4 P1：`public.pem` 是损坏的，人脸核验会失败

**位置**：`assets/key/public.pem`，被 `lib/util/global.dart:705` 的 `encodeString()` 使用

实测比对（与 `sfb_admin` 里那份完整公钥逐字符 diff）：

```
APP 公钥：191 字符 → base64 解码 143 字节  （%4 = 3，长度非法）
后台公钥：216 字符 → base64 解码 162 字节  （合法 1024-bit 公钥）
公共前缀 70 字符，公共后缀 121 字符
后台独有段：'5M9RpcU6uY6kJ67GDEdTZweZI'（25 字符）
```

**即 APP 的公钥被删掉了中间 25 个字符**，不是合法 DER，`RSAKeyParser().parse()` 会抛 `FormatException`。

**影响面**：`encodeString` 只有一个调用点 —— `lib/service.dart:1312` 的 `getAliFaceResult()`（人脸核验结果上报）。所以 **APP 的人脸核验流程走到最后一步会报错**。

**修复**：用后台那份完整公钥覆盖（已验证它与服务端 `rsa.private_key` 配对），或直接从服务端私钥导出公钥重新生成：

```bash
openssl rsa -in private.pem -pubout -out public.pem
```

### 3.5 P1：签名口令硬编码 + 包名是作者的

**位置**：`android/app/build.gradle:37,52-66`

```gradle
applicationId "com.junchen.sanyinghui"

signingConfigs {
    release {
        keyAlias "syh.hzhero.cn"
        keyPassword "123456"
        storeFile file('../keystore/xxx.jks')
        storePassword "123456"
    }
}
```

- `applicationId` 必须换成自己的（否则应用商店包名冲突，且这个包名在 Google Play / 国内商店归属作者）
- 口令 `123456` 是占位符，但**写在仓库里**，改的时候别只改文件不建新 keystore
- `storeFile` 指向不存在的 `xxx.jks`，首次打包会直接失败

**务必**：keystore 文件、口令、`key.properties` 加进 `.gitignore`，绝不入库。

### 3.6 P1：两端都开了明文流量

| 平台 | 配置 | 位置 |
| --- | --- | --- |
| Android | `android:usesCleartextTraffic="true"` | `AndroidManifest.xml:107` |
| iOS | `NSAllowsArbitraryLoads` + `NSAllowsArbitraryLoadsInWebContent` 均为 `true` | `ios/Runner/Info.plist:79-84` |

配合 3.1 的 debug 地址 `http://192.168.1.15:8008`，一旦有人在 release 包里误用 http，中间人可以直接抓包改订单、改提现金额。

**修复**：Android 改 `usesCleartextTraffic="false"` + `networkSecurityConfig` 只白名单调试域名；iOS 删除 `NSAllowsArbitraryLoads`（保留 `InWebContent` 如果支付页确实需要）。

### 3.7 P2：品牌与资源硬编码清单

| 项 | 位置 | 值 |
| --- | --- | --- |
| APP 名称 | `lib/util/global.dart:45` | `APP_NAME = '三盈会'` |
| URL Scheme | `pubspec.yaml:133` | `com.junchen.sanyinghui` |
| Android 包名 | `build.gradle:37` / `namespace:80` | `com.junchen.sanyinghui` |
| 微信 AppID | `global.dart:90` | `wx139d763ebb9a29e0` |
| 微信 Universal Link | `global.dart:91` + `ios/Runner.entitlements:13` | `https://sanyinghui.syh.hzhero.cn/` |
| 企业微信客服 | `global.dart:98` | `ww99c2dedd45f997f9` |
| 首页菜单图 / 红包页图 | `menu_data.dart` / `AliRedPage.dart` 等 | 作者 OSS |
| 隐私协议域名 | `global.dart:52` | `baseDomain = ''`（空，导致协议链接无效） |

`baseDomain` 为空意味着 `privacyUrl`、`userUrl` 等全是 `/protocol/xxx.html` 这样的相对路径——**应用商店审核会因"隐私政策打不开"直接驳回**。这个必须补。

### 3.8 P0：项目当前无法编译

**位置**：`pubspec.yaml:13-15`

```yaml
flutter_z_location:
  git:
    url: https://gitee.com/jacky4631/flutter_z_location.git
```

实测该仓库**已返回 404 / 需认证**：

```
$ git ls-remote https://gitee.com/jacky4631/flutter_z_location.git
remote: Incorrect username or password (access token)
fatal: Authentication failed
$ curl -o /dev/null -w "%{http_code}" https://gitee.com/jacky4631/flutter_z_location
404
```

`pubspec.lock` 里记录了 `resolved-ref: 58207ec6...`，但本地 `%LOCALAPPDATA%\Pub\Cache\git` 没有缓存。

**结论**：任何人拿到这个仓库执行 `flutter pub get` 都会失败——**项目当前状态是不可构建的**。

**好消息**：全项目只用了一行

```dart
// lib/index/local_page.dart:79
var res = await FlutterZLocation.getCoordinate(accuracy: 1);
```

而 `geolocator: ^14.0.3` 已经在依赖列表里（但未被使用）。替换方案：

```dart
final pos = await Geolocator.getCurrentPosition();
// pos.latitude / pos.longitude 替代原 res
```

记得在 `AndroidManifest.xml` / `Info.plist` 里补定位权限（当前三个定位权限都被 `tools:node="remove"` 移除了，只在用到本地生活页时才需要）。

替换后删掉 `pubspec.yaml` 里该依赖，项目即可正常 `pub get`。

### 3.9 P2：上传接口路径疑似拼错

**位置**：`lib/httpUrl.dart:168`

```dart
static const fileUpload = '/api/alioss/upload';
```

`suClient` 的 `baseUrl` 已经是 `https://host/api`，再拼 `/api/alioss/upload` 会得到 `https://host/api/api/alioss/upload`。

服务端如果没做兼容，这个接口 404。验证方法：抓包看实际请求路径，或对一下服务端 `AliOssController` 的 `@RequestMapping`。

## 四、商用授权分析

### 4.1 Flutter 依赖：全部宽松协议

| 类别 | 代表包 | 协议 |
| --- | --- | --- |
| Flutter / Dart SDK | flutter, flutter_localizations | BSD-3-Clause |
| UI 与工具 | dio, shared_preferences, cached_network_image, flutter_svg, flutter_screenutil | MIT / BSD |
| 富文本与媒体 | chewie, webview_flutter, image_picker, photo_manager | MIT / BSD |
| 支付与登录 | fluwx（微信）、tobias（支付宝）、sign_in_with_apple | MIT / BSD / Apache-2.0 |
| 推送与风控 | jpush_flutter（极光）、shanyan（闪验）、appcheck | MIT / 厂商 SDK |

**没有任何 GPL/AGPL 依赖**，Flutter 生态本身就是 BSD-3，闭源商用没有传染风险。

### 4.2 真正的授权与合规成本在厂商 SDK

这部分和服务端的 iText/Aspose 不同——不是"要买 license"，而是**要资质 + 要合规披露**：

| SDK | 要求 |
| --- | --- |
| 淘宝联盟百川（AlibcTradeBiz 等 15 个 aar） | 需完成淘宝联盟媒体备案，AppKey 与包名绑定。**包名改了要重新备案** |
| 极光推送 | 免费版够用，但 AppKey 必须自己注册；隐私政策需列明采集项 |
| 闪验（创蓝） | 需企业实名 + 短信签名审核 |
| 微信开放平台 | 需企业认证（300 元/年），AppID 与包名、签名指纹绑定 |
| 支付宝（tobias） | 需商户资质，私钥证书自己申请 |
| UT 埋点（ut-analytics / utdid） | **必须在隐私政策披露**，否则工信部检测会通报 |

**最容易被忽略的一条**：`utdid4all` 会采集设备唯一标识。2021 年后工信部对"未告知即采集设备信息"查得很严，隐私政策里必须明确写出来，并做到"首次启动弹窗授权后再初始化 SDK"。

### 4.3 三个来自作者 gitee 的 fork 包（已实际审计）

`pubspec.yaml` 里有三个依赖指向作者个人仓库。Flutter 会把它们的代码直接编进 APK，光看 `lib/` 是查不到的，所以我把三个仓库实际拉下来审了一遍：

```bash
git clone --depth 1 https://gitee.com/jacky4631/flutter_alibc.git
git clone --depth 1 https://gitee.com/jacky4631/flutter_ali_face_verify.git
git clone --depth 1 https://gitee.com/jacky4631/flutter_z_location.git   # ← 失败
```

| 包 | 状态 | 审计结果 |
| --- | --- | --- |
| `flutter_alibc` | ✅ 已审计（8 dart + 16 原生文件） | **干净**。网络调用只出现在注释和 example 里（淘宝官方授权 URL）；`MethodChannel("flutter_alibc")` 是标准桥接；无 `getDeviceId`/`ContactsContract`/`SmsManager`/`getInstalledPackages` 等敏感调用 |
| `flutter_ali_face_verify` | ✅ 已审计（8 dart + 5 原生文件） | **干净**。零网络调用、零敏感能力，只有标准 `MethodChannel` |
| `flutter_z_location` | ❌ **仓库 404 / 需认证** | 无法审计，且导致项目不可构建（见 3.8） |

敏感能力扫描（两个已审计的包）：

```bash
grep -rniE "getDeviceId|getImei|ContactsContract|SmsManager|READ_SMS|ClipboardManager|getInstalledPackages|TelephonyManager|android_id" ...
# → 无命中
```

**结论：已审计的两个包没有发现问题**，之前担心的"在 fork 里塞上报代码"没有出现。第三个包已不可访问，反而变成了构建阻塞。

**仍然建议做的事**（供应链卫生，不是安全问题）：

1. 把 `flutter_alibc`、`flutter_ali_face_verify` fork 到自己账号，**锁定 commit**
2. `flutter_alibc` 目前依赖 `ref: HEAD`，作者随时可以 force push，你下次 `pub get` 会拉到新代码——这是真实风险，不是理论风险
3. `flutter_ali_face_verify` 已经用 `ref: 879a4b1...` 钉死了，做法正确

### 4.4 项目自身协议

`LICENSE` 与前两端完全一致：

- **2.1**「以自用为目的，可将本软件用于盈利或非盈利项目，且不受任何限制」
- **2.5**「未经书面许可，不得删除网站底部及相应的官方链接」
- `README` 却写「商用必须保留版权信息，并支付商用授权费用」

同前两端的结论：**自己运营（含盈利）属"自用"，按 LICENSE 2.1 不需付费**；对外交付、多租户 SaaS、转售源码才需要商业授权。

### 4.5 如何"规避"商用授权问题

**可以做的**：

1. **走自用路径** —— 自己运营，保留版权标识，零授权费。
2. **SDK 全部换成自己申请的账号** —— 这不花钱，但必须做（否则等于用作者的账号跑自己的生意）。
3. **三个 gitee fork 包 fork 到自己账号并锁 commit** —— 消除供应链风险，成本很低。
4. **隐私合规补齐** —— 不是"规避授权"，是上架前提：隐私政策、SDK 清单、首次启动授权弹窗。

**不能做的**：

- 删版权标识、官方链接（违反 LICENSE 2.5）
- 破解商业版（违反 2.3）
- 转售源码或安装包（违反 2.2）

## 六、总体判断

代码本身是干净的：没有隐藏上报、没有动态执行、没有原生桥接后门、`package/` 下的本地依赖是死代码。Flutter 生态的依赖也全是宽松协议，比服务端（iText AGPL + Aspose）和后台都省心。

**但它也是三端里"不修改就直接上线"风险最高的一端**。服务端的问题主要是"数据可能被作者看到"，后台的问题是"备案号要换"，而这一端的问题是**整个 APP 的控制权都在作者手上**——数据流向他的服务器、推送走他的极光账号、更新通道由他的服务器决定。任何一条不改，你的业务就跑在别人的地基上。

**三个 gitee fork 包我实际拉下来审了**：`flutter_alibc` 和 `flutter_ali_face_verify` 都是干净的（无敏感能力调用、无隐藏上报），之前的担心可以放下。第三个 `flutter_z_location` 仓库已经 404，反而成了构建阻塞——好在只有一行代码用到它，换成已在依赖里的 `geolocator` 即可。

所以这个项目目前的真实状态是：**代码没有后门，但既编译不了，也跑在作者的地基上**。先解决编译（换掉失效依赖），再按 P0 清单把 API 域名、微信、极光、包名、签名换成自己的，这个 APP 才真正属于你。

改完之后，这一端的授权成本是零——Flutter 依赖 BSD/MIT，按 LICENSE 2.1 自用无需付费。真正要花钱的地方在别处：企业认证、短信签名、应用商店上架，以及淘宝联盟的媒体备案。
